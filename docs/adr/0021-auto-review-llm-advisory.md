# ADR-0021: 자동 검토는 다시 만들지 않는다 — 코드 점검은 경고, LLM 점검은 참고 의견
- 상태: Accepted (2026-10-20)
- 관련 모듈: `ai-server/app/agent/lesson_prep/` (`nodes.auto_review`, `graph.py`, `state.py`), `ai-server/prompts/write_explanation.md`, `write_script.md`, `frontend` (수업안 검토 화면)
- 관련 ADR: [ADR-0013](0013-process-over-model.md) (결정 3 "auto_review의 LLM 검사는 그대로 둔다"를 이 ADR이 바꾼다), [ADR-0020](0020-local-model-for-demo-too.md)

## 배경 (Context)
수업 준비 그래프는 `auto_review`가 실패하면 `plan_lesson`으로 돌아가 설명·대본을 다시 만들고, 3번을 넘기면 경고를 달아 선생님에게 넘겼다. 실패 이유는 다시 만드는 프롬프트에 넣었다.

그런데 [ADR-0013](0013-process-over-model.md) 이후로:
- 구성안은 코드 규칙이다. 코드 점검(ID, 복습, 시간 합계)이 실패한다면 버그이고, 다시 만들어도 같은 결과가 나온다.
- LLM 점검(자연스러움, 문체, 수준, 예문 일치, 대본 분량)은 로컬 qwen3:8b에서 흔들린다. 2026-10-20 유이 수업 준비에서 4번 연속 실패해 재시도 한도까지 돌았고(10분 이상), 실패 이유도 매번 달랐다.
- 어차피 선생님이 범주마다 승인·수정·피드백을 한다 (HITL).

## 결정 (Decision)
1. `auto_review`는 **한 번만** 돌고 결과를 선생님 검토 화면에 붙인다. 그래프는 `auto_review → briefing → human_review`로 곧게 간다. 재시도 루프와 `retry_count`, `MAX_REVIEW_RETRY`를 없앤다.
2. 점검마다 `kind`를 붙인다.
   - `code`: 정답이 있는 점검. **통과 여부(`passed`)는 이것만으로 정한다.** 실패하면 `review_warning`을 켠다.
   - `llm`: 참고 의견. 화면에 "AI 참고 의견 — 틀릴 수 있어요"로 따로 보여 주고, 통과 여부에 넣지 않는다.
3. 설명·대본 프롬프트에서 "자동 검토에서 지적된 문제" 칸을 뺀다. 다시 만드는 근거는 선생님 피드백뿐이다.

## 검토한 대안 (Alternatives)
| 대안 | 설명 | 장점 | 기각 이유 |
|---|---|---|---|
| 재시도 한도만 줄이기 (3 → 1) | 루프는 두고 한 번만 | 변경이 작다 | 흔들리는 판정으로 다시 만드는 일은 그대로다. 한 번이라도 수업 준비 시간이 두 배가 된다 |
| LLM 점검 빼기 | 코드 점검만 | 가장 빠르다 | 문체가 섞이거나 대본이 너무 짧은 경우 같은 힌트를 선생님이 잃는다 |
| LLM 점검을 범주별로 나눠 작게 | 판정을 안정시키기 | 판정 품질이 오를 수 있다 | 호출이 4배가 된다. 재시도를 일으키지 않는다면 지금 판정으로도 참고에는 충분하다 |

## 결과 / 트레이드오프 (Consequences)
- 좋은 점: 수업 준비가 설명 → 대본 → 검토 → 브리핑 한 바퀴로 끝난다. 로컬 모델에서 걸리는 시간을 예측할 수 있다.
- 좋은 점: 선생님이 보는 "통과"가 정답이 있는 점검만 뜻하게 된다.
- 대가: LLM이 잡아내던 문제(문체 섞임 등)를 자동으로 고치지 않는다. 선생님이 참고 의견을 보고 피드백을 줘야 한다.
- 대가: 기획 ADR-0020의 주 지표(첫 검토 승인 비율)에는 불리할 수 있다. 다시 만들어 고치던 초안이 그대로 선생님에게 간다.

## 재검토 조건
- 선생님이 LLM 참고 의견과 같은 이유로 피드백을 자주 준다면 → 그 점검만 코드로 바꾸거나(예: 대본 글자 수), 그 범주만 자동으로 한 번 다시 만든다
- 더 큰 모델을 쓰게 되면 → LLM 점검을 다시 통과 여부에 넣는 것을 검토한다
