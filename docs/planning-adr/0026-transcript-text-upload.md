# ADR-0026: 수업 후 기록에 녹취록 텍스트 파일(.txt)도 받는다 — STT는 서비스 밖에서
- 상태: Accepted (2026-10-21), 4번 글자 수 상한만 Superseded by [ADR-0029](0029-understanding-from-transcript-drives-review.md) (2026-10-21)
- 관련 모듈: `frontend/src/pages/LessonRecordPage.vue`, `ai-server/prompts/extract_record.md`
- 기술 설계: [docs/adr/0029](../adr/0029-nav-student-prep-tabs.md) (화면 구성)
- 관련 ADR: [ADR-0003](0003-lesson-record-input.md) (P2 녹음 파일 항목을 이 ADR이 대체), [ADR-0009](0009-hitl-on-all-writes.md), [ADR-0011](0011-virtual-data-only.md)

## 배경 (Context)
- ADR-0003은 수업 기록을 텍스트 메모로 받고, 녹음 파일 분석은 P2(STT 포함)로 미뤘다.
- 수업 녹음을 텍스트로 바꾸는 일은 휴대폰·회의 앱의 받아쓰기 기능으로도 이미 할 수 있다. 서비스가 STT까지 맡을 필요는 없다.
- 선생님에게 필요한 건 "녹음으로 받아 적은 텍스트를 그대로 올리는" 입구다. 마감(2026-10-22) 전이라 정확한 분석보다 올릴 수 있는 것이 먼저다.

## 결정 (Decision)
1. 수업 후 기록 화면에 **"녹취록 파일 불러오기 (.txt)"** 버튼을 둔다. 브라우저에서 파일을 읽어 메모 칸에 넣는다. 메모가 이미 있으면 그 아래에 덧붙인다.
2. 이후 흐름은 메모와 같다. 같은 `post_lesson` 그래프로 초안을 만들고, 선생님이 항목별로 승인한다 (ADR-0009). 원문은 `rawNote`로 저장한다.
3. **STT(음성 → 텍스트)는 서비스 밖에서 한다.** 오디오 파일은 받지 않는다.
4. 글자 수 상한은 지금처럼 8,000자다. 넘으면 화면에서 막고, 핵심 부분만 남기도록 안내한다.
5. 추출 프롬프트에 "메모가 T/S 대화 녹취록일 수 있다"는 한 줄만 더한다. 녹취록 추출 정확도는 이번 목표가 아니다.
6. 테스트용 가상 녹취록: `ai-server/data/samples/transcript_sample_ja.txt` (3과, 사토 유이, 약 1,500자).

## 검토한 대안 (Alternatives)
| 대안 | 설명 | 장점 | 기각 이유 |
|---|---|---|---|
| A. 메모만 유지 (ADR-0003 그대로) | 녹취록은 받지 않음 | 할 일 없음 | 녹음을 이미 텍스트로 가진 선생님도 메모를 다시 써야 한다 |
| B. 오디오 업로드 + 서버 STT | Whisper 등으로 변환 | 선생님이 가장 편함 | 긴 오디오, 화자 구분, 의존성 추가, 음성 개인정보. 마감 안에 어렵다 |
| C. 녹취록을 서버에 따로 저장하는 새 API | 파일 업로드 엔드포인트 | 원본 파일 보관 | 지금 필요 없다. 텍스트는 이미 `rawNote`로 저장된다 |
| D. 상한을 늘려 50분 녹취 전체 받기 | 3만 자 이상 | 자르지 않아도 됨 | 로컬 모델 컨텍스트(16k 토큰)를 넘는다. 정확도 목표도 없다 |

## 결과 / 트레이드오프 (Consequences)
- 좋은 점: 백엔드·API 변경 없이 프론트와 프롬프트 한 줄로 끝난다.
- 대가: 50분 녹취 전체는 8,000자를 넘기 쉽다. 선생님이 핵심 부분을 골라 붙여야 한다.
- 대가: 녹취록에서 뽑은 초안은 메모보다 부정확할 수 있다. 항목별 승인으로 거른다.
- 실제 학생 녹음은 쓰지 않는다. 가상 녹취록만 쓴다 (ADR-0011).

## 재검토 조건
- 녹취록을 자주 올리고 8,000자 제한이 불편하면 → 요약 노드를 앞에 두거나 상한을 늘린다 (기술 ADR 필요)
- 받아쓰기 앱을 따로 쓰는 게 번거롭다는 의견이 쌓이면 → 오디오 업로드 + STT(대안 B)를 다시 검토한다
