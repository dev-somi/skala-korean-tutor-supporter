# TS-0003: 인쇄 33쪽이 PDF 33쪽(과 표지)으로 바뀌어 엉뚱한 쪽이 열렸다
- 날짜: 2026-10-21
- 관련 모듈: `ai-server/app/rag/pdfs.py` (`page_table`)
- 관련 ADR: [기술 ADR-0030](../adr/0030-local-pdf-open-via-ai-server.md)

## 증상
출처의 쪽(책에 인쇄된 쪽)을 PDF 쪽으로 바꾸는 표를 OCR JSON 꼬리말로 만들었다. 지침서 1권 3과 「학습 목표·수업 개요」(인쇄 32~33쪽)가 PDF `[35, 33]`으로 나왔다. 앞쪽은 맞고 뒤쪽만 틀렸다.

```
학습 목표·수업 개요 [32, 33] → [35, 33]     ← 33은 36이어야 한다
```

## 원인
처음 구현은 쪽마다 `printed_page(lines) or page["page"]`를 키로 `setdefault`했다. 청크 단계와 같은 규칙이다. 그런데 PDF 33~34쪽은 과 표지라 꼬리말 쪽 번호가 없어서 PDF 쪽 33이 키로 들어갔다. 진짜 인쇄 33쪽(PDF 36쪽)보다 먼저 나와서 자리를 차지했다.

표를 고친 뒤 책마다 "인쇄 쪽이 커지면 PDF 쪽도 커지는가"를 검사하자, OCR이 꼬리말 숫자를 잘못 읽은 쪽(실용 2권: 9쪽을 "92"로 읽음)도 같은 인쇄 쪽에 PDF 쪽 두 개를 만들고 있었다.

## 시도한 것
| 시도 | 결과 |
|---|---|
| 쪽 순서대로 `printed or pdf`를 `setdefault` | 쪽 번호 없는 쪽이 인식된 쪽 번호를 가로챔 |
| 인식된 쪽 번호를 먼저 채우고, 없는 쪽은 빈 키에만 | 과 표지 문제 해결. 잘못 읽은 숫자는 남음 |
| 같은 인쇄 쪽 후보 중 책의 보통 차이(PDF − 인쇄의 중앙값)에 가까운 쪽 | 잘못 읽은 숫자 대부분 해결. 24권 중 2권에 몇 쪽 남음 |

## 해결
`page_table`: ① 인식된 쪽 번호만, 보통 차이에 가까운 순서로 채운다 ② 쪽 번호가 없는 쪽은 남은 빈 키에만 넣는다. 테스트 `tests/test_pdfs.py::test_page_table_skips_unnumbered_and_misread_pages`.

## 배운 점 / 다음에 주의할 것
- 대신 넣은 값(fallback)이 진짜 값과 같은 공간을 쓰면 충돌한다. 진짜 값을 먼저 채운다.
- OCR에서 뽑은 숫자로 표를 만들면 단조성(쪽이 커지면 같이 커지는가)을 한 번 검사한다.
